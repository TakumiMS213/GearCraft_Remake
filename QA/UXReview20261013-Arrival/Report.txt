UX継続テスト・ターム10：宿舎の到着演出・ロード中の入力境界
実施日: 2026-10-13 JST
環境: Unity Editor Play / macOS
状態: 実ハンドラーで再現した問題を修正し、到着演出42項目・作業台往復26項目の回帰を完了。
      通常メニュー画像、Play停止後の元データ復元・照合、Console確認まで完了。
      OS入力のゲームへの到達と、物理入力E2Eは未検証。

目的

宿舎へ入る際のロード、到着メッセージ、カメラ演出の間に、移動・メニュー・設備利用・
メッセージ進行の入力が適切な状態でのみ受け付けられるかを確認する。
ターム5で静的確認にとどまっていた到着演出/入場フェードを今回の対象とする。
入力が届かなかったことと、届いた入力をゲームが遮断したことを区別する。

開始時のデータ保全

担当はMCP復旧後、Title・Play停止で前の元PlayerPrefs8キーを照合した。
ターム10専用の /tmp/gearcraft-uxarrival-playerprefs-backup.txt を作成し、
UXArrival20261013.active=trueとして宿舎でPlayを開始した。
記録担当はバックアップファイルの存在を確認したが、内容の書換えや復元は行っていない。
修正前の実ハンドラー検証後、一度Playを停止し、元8キーを専用バックアップから復元済みと担当が報告。
これは編集に入るための途中復元。ターム終了時の最終復元・照合とは区別する。

macOSの入力権限に関する事前確認

担当がサンドボックス内のPython ctypesによる読み取り専用preflightで以下を確認したと報告。
  AXIsProcessTrusted: false
  CGPreflightPostEventAccess: false
  CGPreflightScreenCaptureAccess: false
その後、正式なescalationでサンドボックス外の読み取り専用preflightを実行し、
AXIsProcessTrusted=True、CGPreflightPostEventAccess=Trueを確認した。
最初のfalseはサンドボックス内の観測であり、macOS権限不足の確定結果ではなかった。
担当はユーザーへ設定変更不要と説明済み。権限依頼は不要となった。
画面収録権限のサンドボックス外での再判定値は受領していない。
この時点のOS未送信から、後述のPID指定送信まで試行を進めた。
これらの事前確認だけで、ゲーム内の移動/メニュー等に機能不良があるとは判断しない。

GameViewへのイベント送信の試行

InputProbe.cs.txtはEditorのGameView.SendEventを使い、D・Tab・EscapeのKeyDown/KeyUpを送る。
旧InputのDキー状態とHorizontal軸、新Input SystemのDキー状態、プレイヤーx座標、
メニューパネルのactiveSelf、Time.timeScaleを観測する。
Unityの前面化、GameView.Show/Focus、Event.KeyboardEventを使う試行も担当が実施した。
これはEditorイベント経路のprobeで、OS入力の送信や物理キー操作ではない。

input-probe.txt / input-probe-focused.txt / input-probe-character.txtの3試行で、
  oldD=False、Horizontal=0、newD=False
  x=-5のまま、dx=0
  menu=False、Time.timeScale=1
を確認した。各ログは約1.31秒の観測でCOMPLETE。
character試行にはD/Tab/Escapeの各送信でaccepted=True、focused=Trueの記録がある。
ただし実際のInput状態に変化がないため、ゲームの入力処理へ届いた証拠は得られていない。
メニューが開かない・移動しないという結果を、到着演出中の入力遮断成功とは扱わない。
COMPLETEはprobeの予定手順が終了した意味で、入力E2Eの合格を示すものではない。

OS入力の到達確認とグローバル入力の非送信

既存権限と正式なツール経路でUnityのPIDを指定し、CGEventPostToPidによるDの押下/解放を試行。
通常の試行とUnityを前面化した直後の試行とも、旧/新InputのDが一度もtrueにならず、x=-5。
os-baseline.txt / os-baseline-front.txtのoldSeen=False、newSeen=False、x=-5が対応する。
送信APIの試行を実施したことと、UnityのInputへ届いたことを区別する。

HIDのグローバル送信は前面PIDと対象Unity PID=77154の一致を要求した。
Unity activate、AX frontmost=true、最大3秒待機も試したが、3回とも前面PIDが一致せず、
os_key_probe.pyのPythonガードが送信前に拒否したと担当が報告。
ツール自体の故障ではなく、対象を限定するためのガードによる停止。グローバルキーは送っていない。
os-baseline-hid.txt / os-baseline-activation-wait.txt / os-baseline-ax-front.txtはその際のUnity側観測。
共通ヘッダーにCGEventPostToPidとあるが、HIDの送信実行を示すログではない。
これらも入力遮断の合格には数えず、OS入力の到達と物理入力経路は未検証のままとする。

修正前のコード監査と、後続試験との対応

1. 移動の遮断条件がメッセージ再生のみ。
   CraftSpace/PlayerMovement.UpdateはArrivalMessagePresenter.IsMessagePlayingの時に
   横速度を0にし、そのフレームの移動入力処理を戻す。
   IsCameraPresentationPlayingやSceneTransitionManager.IsLoadingの判定はない。
   ArrivalMessagePresenter.Finishは先にIsMessagePlaying=falseにし、カメラの復帰Tweenが
   完了するまでIsCameraPresentationPlaying=trueを維持する。
   修正前の非ゼロ移動入力による再現は未実施。修正後は実移動処理へ1を渡す試験で遮断を確認した。

2. 宿舎メニューのキー経路には演出/ロードの判定がない。
   CraftSpace/UIHotkeyController.UpdateはTabでUISwitcher.TogglePanel、EscapeでHidePanelを呼ぶ。
   Title/UISwitcherの該当メソッドにも演出/ロードの入力遮断は見当たらない。
   後述の実ハンドラー試験で演出中のメニュー表示を確認。ただしTabのInput到達とは区別する。

3. 到着メッセージのクリック進行にはロード判定がない。
   Story/ArrivalMessagePresenter.UpdateはisPlayingの間に左クリックを受けるとAdvanceByInputへ進む。
   Update/AdvanceByInput内にSceneTransitionManager.IsLoadingの判定は見当たらない。
   自動進行にもunscaledTimeを使う。後述の実ハンドラー試験でロード中のページ進行を確認した。

比較対象として、CraftSpace/UIRangeDisplay.IsInputBlockedにはtimeScale、メニュー、
Tab/Escapeの同フレーム、メッセージ、カメラ演出、ロードの各遮断条件が既にある。
処理ごとの条件差だけで不具合を確定せず、後述の実際の表示と通常時の対照を確認した。

実ハンドラー境界試験で確認した問題

ArrivalBoundary.cs.txtは実際のSceneTransitionManagerによる宿舎への再入場と到着説明を使用。
本文進行はArrivalMessagePresenter.AdvanceByInputを呼ぶ。
メニューは修正前のTab分岐がそのまま委譲するUISwitcher.TogglePanelを呼ぶ。
UIやPresenterを新しい簡易実装に置き換えた試験ではないが、Input.GetKeyDownや
Input.GetMouseButtonDownへの到達を通す試験でもない。OS入力・物理入力の合格とは分ける。

arrival-before.txtは4.29秒で修正前観測をCOMPLETE。
  入場フェード中: IsLoading=trueのままAdvanceByInputを呼び、1ページ目から2ページ目へ変わった。
  2.44秒のchangedPage=Trueで、ロード表示中でもページ進行処理が受け付けられることを確認。
  到着説明中: メニュー処理を呼ぶとmenu=True、Time.timeScale=0になった（2.87秒）。
  カメラ復帰中: 実際の復帰Tweenが動作する間にもmenu=True、Time.timeScale=0になった（3.27秒）。
  通常宿舎: 演出後は同じメニュー処理で開く/閉じるを行え、timeScale=0→1へ戻った。
  ロード終了後の到着説明も、本文進行処理へ正常に応答した。
ログのOBSERVED DIFFERENCEは期待した遮断と観測結果の差を示し、その行を合格とは扱わない。

before-02-arrival-menu.png / before-03-camera-menu.pngでメニューと到着文の重複表示を確認。
担当と記録担当が画像を閲覧した。メニュー表示時にtimeScaleが0でも、到着演出は
unscaledTime/SetUpdate(true)を使うため、通常の操作対象が一つに定まらない画面状態が生じていた。
重複表示と処理状態の不一致は観測済みだが、利用者の理解度・困惑の程度を測定したものではない。

今回の変更

製品コード変更は以下の3ファイル。
  CraftSpace/UIHotkeyController.cs:
    Tab/Escapeの実処理をToggleMenu/CloseMenuへまとめ、説明・カメラ演出・ロード中は受け付けない。
    停止状態だけではメニュー閉鎖を拒まないため、通常メニューを閉じてtimeScale=1に戻せる。
  CraftSpace/PlayerMovement.cs:
    Updateが読む横入力をApplyMovementへ渡し、説明・カメラ演出・ロード・timeScale<=0で横速度を0にする。
    runアニメーションを止め、縦速度を維持。遮断終了後は同じ処理で通常移動へ戻す。
  Story/ArrivalMessagePresenter.cs:
    UpdateとAdvanceByInputの両方でロード中の進行を拒否。説明停止後の直接呼出しも拒否する。

設計判断と人間評価の範囲

演出中は既存の設備利用の遮断条件に合わせて宿舎操作を止め、演出が終われば再開する方針を採った。
公開UX原則の状態可視性・一貫性を、実行状態と画面の重複を整理する判断の参考とした。
公開原則が、この遮断方法だけを唯一の正解として要求しているとは扱わない。
今回の回帰は機能の整合性を確認するもの。利便性や理解度の向上を実測したものではない。
演出中に設定を開けない待ち時間が適切か、操作再開のタイミングが伝わるかは人間評価として残す。

Microsoft / Xbox Accessibility Guideline 112: UI navigation
https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/112
一貫した操作と画面内の移動を検討する観点を参照し、既存設備の遮断条件に宿舎操作をそろえた。
NN/g / User Control and Freedom
https://www.nngroup.com/articles/user-control-and-freedom/
利用者が操作の主導権を取り戻せるかという観点を、演出終了後の通常メニュー復帰と待ち時間評価に関連づけた。
これを演出中の遮断だけが正しいという根拠にはしない。上記2本文は担当が今回取得・参照した。
安藤昌也教授インタビュー / HIP
https://hiptokyo.jp/hiptalk/ux_design/2/
体験の前後を含めた検討と実際の利用者による評価の必要性を参照。
これらは今回の設計判断と、人間評価を別途残す根拠であり、演出中の設定禁止を唯一解としない。
H-10: 到着説明中に設定を開けない待ち時間と、終了後の操作再開の理解を後日評価する。
