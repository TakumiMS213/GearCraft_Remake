4件目：宿舎修理2回の配分感度
label=gate_sensitivity_IC408_GearCraft_speed6_gear8_repair2_seed77。
seed77 / ic_speed_budget / Gear8 / BOOST6 / HP100は同じ。初期門200は2夜の宿舎修理+50×2を選んだ配分、STR/ACC各1は元各4から2夜の食事期待値各3を引いた比較用到達値。食事と修理を無条件に併用して有利にする条件ではない。

rootの追加setup（mainrunnerを変更しない）
通常bootstrapで、各CSV行に対応する GearCraft,7,ic_speed_budget,seed をTitleからMainへ準備する。READY・timeScale0・戦闘開始前に通常の初期値を適用した後、下記を一度だけ行い、それからCaptureDayStartSnapshot、最後に追加routeを呼ぶ。

var sensitivityMaterials = MaterialManager.Instance;
if (sensitivityMaterials == null || Time.timeScale != 0f ||
    StageCounter.Instance == null || StageCounter.Instance.StageCount != 7 ||
    StageFlowManager.Instance == null || StageFlowManager.Instance.IsStageActive)
    throw new System.Exception("Sensitivity carry requires paused pre-battle Main wave7");
if (sensitivityMaterials.GetMaterial(MaterialManager.MaterialType.Gear) != 0)
    throw new System.Exception("Expected cleared initial Gear; refusing duplicate carry setup");
sensitivityMaterials.gear = 8;
// Existing root setup follows with CaptureDayStartSnapshot before invoking route.

初期値として公開fieldへ代入する理由：AddMaterialはStageFlowManager.RecordMaterialGainedへ入り、過去日からの持込を当日の獲得素材として計上してしまう。MaterialManager.LateUpdateは表示変更を通知する。routeのinitial-materials.jsonはgear8を記録する。実行setupログにも「initial_carry Gear0→8; model-budgeted; before battle」と明記する。
戦闘開始後にはGear/HP/門を追加しない。ボス出現時には前座回収や報酬でGear8より多くなってよい。BOOSTは手持ち在庫をnative UseMaterialで1個ずつ消費し、通算6回まで。

独立batch（生成済み）
python3 QA/DefenseBalance20261016/build_sensitivity_batch.py
これにより最新のnative bootstrap / template / 6回routeを読み、BatchDefenseSensitivity.cs.txt と sensitivity-batch-build-manifest.json のみへ出力する。main generatorの小さなpure helper関数はimportするがmain()を呼ばないので、共通manifestを一時上書きすることもない。通常14条件とrepeatのrunner/manifest/template/planなど13ファイルを生成前後のバイトhashで保持確認する。
生成版だけSnapshot前へ上記Gear8処理とinitial_carryイベントを追加。route前にGear8/flat1/速度.5527125/Module0/モジュールflags、そしてcase行のSTR/ACC/HP/門とPlayerのSTR/ACC同期をValidateし、sensitivity_validatedイベントへ記録する。sidecarを含む入力hashを実行時に確認し、変更があれば再生成を要求する。CSVのCRLFを含めFile.ReadAllBytesと同じhashになることも静的確認済み。
独立batchを使う場合、追加setupを外から二重に実行しない。生成版はGear0を期待し、既に8なら安全に停止する。main batch完了後、安定したTitle Playから生成版をrootが実行する。RUNNING/cancel guard、既存result/部分ログの上書き拒否、scene安定待ち、native cleanup、Watchdogは最新templateを保持する。
batch-progressやnative-survival-progressなど共通の実行調整ファイルは順次利用するため、通常14条件と同時実行しない。イベント類はsession timestampと独立case labelで区別する。4条件終了後は既存のroot復元手順でPrefs8・Editor設定・開始画面を戻す。
